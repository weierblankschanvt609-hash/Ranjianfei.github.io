04 / TECHNICAL REVIEW

高频技术问答

点击问题展开。回答先说结论，再讲原理，最后落到项目。

01请用一分钟介绍这个毕业设计。＋

我做的是一个面向 Dobot 机械臂的 Python 中控原型。前端通过 WebSocket 与 FastAPI 实时通信，后端分别连接机械臂控制端口和视觉端，同时接入 Vosk 离线语音识别。语音经过高通滤波和 RMS 能量门处理，再由大模型把自然语言转换成受约束的 JSON 指令，最后由调度层分发。开发过程中使用了 Gemini 辅助编程，我主要围绕需求、设备连接、功能验证和联调迭代推进，并对关键代码进行了复盘。

02这份代码是你完全独立写的吗？＋

不是每一行都由我从零手写，开发中使用了 Gemini 辅助。我不会把 AI 生成等同于自己完全掌握；我能说明系统为什么这样分层、设备端口和协议如何配置、功能如何验证，也能指出当前版本在 TCP 分帧、重连安全、异常处理和机器人指令校验上的不足。对我来说，AI 是加速实现的工具，最终能否接上设备、跑通流程、定位问题和对结果负责，仍然需要工程判断。

03你当时怎么处理 TCP 粘包、拆包？＋

TCP 是字节流，send 和 recv 没有一一对应关系。当前原型通过命令末尾 CRLF、串行化 send/recv 和协议固定响应，降低了出错概率，但 recv(1024) 加正则并不能从根本上解决粘包和半包。工程化做法应该维护接收缓冲区，按协议的分隔符或长度字段循环提取完整帧，未完整的数据留到下一次 recv，并加入超时、长度上限和校验。视觉端不追加换行，是因为对方采用触发码完全匹配，这是双方协议约定，不是通用拆包方案。

04为什么同时用了 asyncio 和 threading？＋

FastAPI/WebSocket 适合用 asyncio 管理等待型 I/O；但机器人 Socket、麦克风采集和部分 SDK 是阻塞接口，所以用 asyncio.to_thread 或后台线程隔离，避免卡住事件循环。线程回传 WebSocket 时用 run_coroutine_threadsafe 切回原事件循环，同一机器人 Socket 的请求和响应用 Lock 保证成对执行。严格说，这是避免阻塞事件循环，并不是‘解决 GIL 死锁’。

05为什么机器人用了两个 TCP 端口？＋

项目把控制面板类指令和运动类指令分开：29999 用于使能、清错、I/O 等控制指令，30003 用于关节或直线运动。代码分别维护 dash_sock 和 move_sock，由 port 字段选择通道，贴合设备 API 的通道定义。

06为什么选择 WebSocket，而不是普通 HTTP？＋

控制端不仅要发送指令，还要持续接收连接状态、日志和关节角度。WebSocket 建立长连接后可以双向主动推送，交互延迟更低，也不需要前端频繁轮询。连接机器人和调用模型这类阻塞任务仍需移出事件循环。

07滤波和降噪具体做了什么？＋

采样率是 16 kHz，先用 5 阶、200 Hz 截止频率的巴特沃斯高通滤波器削弱低频机械与环境噪声，再计算短时 RMS；低于阈值的音频块置零，高于阈值才交给 Vosk。优点是简单、实时、可离线，局限是固定阈值对环境变化不够鲁棒，后续可做噪声标定、动态阈值、连续滤波器状态或 VAD。

08系统掉线以后是怎么恢复的？＋

RobotClient 保存 IP，发送异常时关闭旧连接并重建两个通道。复盘后我认为运动指令不能一律自动重发：如果指令已到达而响应丢失，重发可能造成重复动作。更安全的方案是区分幂等指令和运动指令，结合序号、ACK、机器人状态与执行队列确认，再决定重试。

09如果把这个原型用于真实产线，你首先改什么？＋

第一是安全边界：指令白名单、参数范围、软限位、工作空间校验、模式与使能条件。第二是可靠通信：完整帧解析、心跳、状态机、ACK 和有限重试。第三是配置与审计：密钥放环境变量、分级日志、操作记录。第四是任务队列与完成反馈，不能只收到 API 应答就认为运动结束。
